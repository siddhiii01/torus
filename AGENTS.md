# AGENTS.md: rules for AI coding agents in this repo

This file is the contract for any AI coding agent (Claude Code, Codex, Cursor, others) working in `torus`. Read it fully before writing code. Humans review results. Agents write the code, write the tests, run the tests, and report the evidence.

Related files:

- `SKILLS.md`: step-by-step recipes for recurring tasks (add a reader, add an Excel column, add a validator, and so on). Use the matching recipe instead of improvising.
- `docs/IMPLEMENTATION_PLAN.md`: the phase-by-phase plan. Work is picked from there.
- `docs/AGENT_PROMPTS.md`: copy-paste briefs to dispatch one agent per task (or a phase coordinator). Use with the shared preamble in that file.
- `docs/SETUP.md`: environment setup and **per-model hardware requirements**. Read it before enabling or downloading any model.

If this file conflicts with an older document (for example `PLAN.md`, which describes the earlier procurement-OCR work), **this file and `docs/IMPLEMENTATION_PLAN.md` win**. In particular, there is **no restriction on model origin**. Models are chosen on measured results and licence alone.

---

## 1. What we are building

A local document engine that takes **any PDF or image** (scanned, photographed, handwritten, any layout, any language) and **fills the columns of an Excel template** supplied by the client.

```
file → pages → clean up → page type → find fields → read (many readers) → vote
     → validate → map to Excel columns (LLM, with evidence) → status → Excel + review queue
```

The output is **only** the Excel columns the client defines. We do not build a general "extract everything" system. Every column in the template is described in configuration (a *field spec*), and the pipeline exists to fill those columns correctly.

The quality target is **zero silent errors**. A value marked `confirmed` must be right. Anything uncertain is marked `needs_review` and goes to a person. Each human correction becomes training data.

## 2. Non-negotiable rules

### 2.1 No hard-coding of documents

- **No customer, vendor, bank, form, person or place names in code.** Not in conditions, regexes, string fixes or comments that drive behaviour.
- **No page coordinates in code.** No `x0 > 0.24`, no "landline box at 71.5%". Positions are found at run time, relative to detected anchors (labels, lines, boxes). If a form family needs layout hints, they live in a config file under `config/`, never in Python.
- **No `page == 0` assumptions.** The page that holds a field is decided by page classification plus the field spec.
- **No per-sample "fixes"** (for example, "turn AIN into ANI" or "swap S for B in surnames"). If a reader keeps confusing characters, the fix belongs in the reader (fine-tuning), in voting, or in a validator, never in a string patch.
- **Litmus test:** if a change only makes sense because of one specific document, it is wrong. A new document of a new layout must run through the same code with, at most, new **config**.

### 2.2 Configuration over code

Everything that describes *documents* or *the client* is data:

| What | Where |
|---|---|
| Excel template columns, field types, validators, which page types to look in | `config/templates/<template_id>.yaml` |
| Page types and their descriptions and examples | `config/page_types.yaml` |
| Readers, their models, the hardware each needs, enabled/disabled | `config/readers.yaml` |
| Pipeline thresholds (dpi, confidence cut-offs, voting rules) | `config/pipeline.yaml` |
| Lookup tables (PIN master, state lists) | `resources/lookups/` (public data only) |
| Form-family hints (auto-learned label layouts) | `config/families/*.yaml` (generated, reviewed) |

Code reads config through one typed loader (`torus.config`). Config is validated with pydantic models at start-up, and an invalid config fails loudly.

### 2.3 Data safety (bank documents)

- **Never commit real customer documents, page images, OCR text, crops or answer keys.** Real data lives outside the repo, in the folder set by the `TORUS_DATA_DIR` environment variable. Tests use **synthetic fixtures** generated by code (`tests/fixtures/synth/`).
- **Never log document content.** Logs carry metadata only: file hash, page count, reader name, timings, confidence summaries, status codes. Use `torus.logging.get_logger`, which redacts by default.
- **No document content goes to any external API or cloud service.** All models run locally, either in-process or on a local model server (Ollama, vLLM, or similar) on `localhost` or on the internal network.
- Do not print document text in test output, error messages or exceptions. Refer to fields by key and page index.

### 2.4 No hidden dependencies

- Each stage depends only on the **interfaces** in `torus.core` (the data models and the `Reader`, `PageClassifier`, `Validator`, `FieldMapper` protocols), never on another stage's internals.
- Readers and models are **plugins**, registered in `config/readers.yaml` and loaded by name. The pipeline must keep working when any optional reader is missing or disabled. Fewer voters means lower confidence, never a crash.
- Heavy imports (torch, paddle, transformers, vllm) happen **inside** the reader that needs them, never at package import time.
- No network calls in the pipeline except to configured local model servers.
- Pin dependencies in `pyproject.toml`. Put optional model stacks behind extras (`pip install -e ".[paddle]"`, `".[vlm]"`).

## 3. Architecture

### 3.1 Package layout (target)

```
src/torus/
  core/         data models (pydantic) + protocols. No heavy deps. Everything imports this.
  config/       typed config loader and schemas
  ingest/       PDF/image → Page objects (render, split, embedded text if usable)
  preprocess/   orientation, deskew, denoise, stroke repair, blank detection
  classify/     page-type classifier (multi-pack splitting, routing)
  layout/       regions, label anchors, comb boxes, checkboxes, tables, stamps, signatures
  readers/      one module per reader family, all behind the Reader protocol
  consensus/    character-level alignment + voting, calibrated confidence
  validate/     validators (format, checksum, lookup, cross-page agreement)
  mapping/      LLM field mapper: field specs + evidence → column values with source boxes
  output/       Excel writer: fills the client template, adds status/evidence sheet
  review/       review UI and correction store
  learn/        dataset export from corrections, fine-tune jobs, model registry
  eval/         scoring, test-set management, regression reports
  service/      HTTP API + batch runner (later phases)
  logging.py    metadata-only logger
config/         all document/client knowledge (YAML)
resources/      public lookup tables
tests/          unit/, integration/, fixtures/synth/
docs/           plan, setup, decision records
legacy/         old scripts kept read-only until replaced (do not extend)
```

### 3.2 Core data model (`torus.core`)

Every stage passes these objects and nothing else:

- `Document`: id (content hash), source path, pages, metadata.
- `Page`: index, image (lazy), size, orientation, `page_type`, quality flags (`blank`, `low_quality`, `rotated`).
- `Region`: page index, bbox (normalised 0–1, top-left origin), kind (`text_line`, `field_value`, `comb`, `checkbox`, `table_cell`, `stamp`, `signature`, `photo`), optional label anchor.
- `Reading`: region id, reader name and version, text, per-character confidences if available, raw score, time taken.
- `Candidate`: the voted value for a region: text, agreeing readers, calibrated confidence.
- `FieldValue`: column key, value, `status` (`confirmed` | `likely` | `needs_review` | `not_found`), confidence, `evidence` (a list of region ids with page and bbox), validator results, and the reason when not confirmed.
- `ExtractionResult`: document id, template id, rows (a list of dicts of column key → `FieldValue`), timings, and the versions of every model and config used.

Every `FieldValue` that has a value **must** have at least one evidence region. A value without evidence is rejected by the pipeline.

### 3.3 Key protocols

```python
class Reader(Protocol):
    name: str
    def capabilities(self) -> ReaderCaps: ...            # scripts, handwriting, printed, layout, per-char conf
    def read(self, image: Image, region: Region, hint: ReadHint) -> Reading: ...

class PageClassifier(Protocol):
    def classify(self, page: Page) -> PageTypePrediction: ...

class Validator(Protocol):
    name: str
    def check(self, value: str, ctx: ValidationContext) -> ValidationResult: ...

class FieldMapper(Protocol):
    def map(self, doc: Document, candidates: list[Candidate], template: TemplateSpec) -> list[Row]: ...
```

`ReadHint` carries the expected character set (digits, letters, alphanumeric), expected script or language, and the expected length, all taken from the field spec. Readers use it to constrain decoding.

### 3.4 Design principles

1. **Read many times, trust nothing once.** Important fields get readings from at least two different reader families before they can be `confirmed`.
2. **Locate, then read.** Find the region first (layout), then read the crop. Whole-page model output is used for discovery and context, not as the final value of a critical field.
3. **Validate, never guess.** A value that fails validation is never "corrected" by a heuristic. It goes to review with a reason.
4. **Measured confidence.** Confidence is calibrated on the evaluation set (how often a value with this score was right). Never invent a confidence formula.
5. **Swappable everything.** A better model replaces an older one by changing config and re-running evaluation. No pipeline code changes.
6. **Deterministic and reproducible.** Fixed seeds, temperature 0 for LLMs, and every result records model versions and the config hash.

## 4. Coding standards

- Python 3.12, `src/` layout, type hints everywhere. `mypy --strict` on `src/torus/core`, `config`, `consensus`, `validate`, `mapping`. Normal `mypy` elsewhere.
- Format and lint: `ruff format` + `ruff check`. Run them before every commit.
- Data models use pydantic v2. No loose dicts crossing module boundaries.
- Functions stay small and pure where possible. Image in, data out. No global state. Models load lazily and are cached per process.
- Errors: raise typed exceptions from `torus.core.errors`. Never swallow an exception silently. A reader failure becomes a `Reading` with `error` set, and the pipeline continues.
- Naming: modules and functions in `snake_case`, classes in `PascalCase`, config keys in `snake_case`.
- Comments explain **why**, not what. No commented-out code.
- No new top-level dependencies without a line in the PR description saying why. Optional model stacks go in extras.
- Do not add to `legacy/`. Port what is useful into `src/torus/` with tests, then delete the legacy file.

## 5. Testing: agents must prove their work

Every change ships with tests, and the agent runs them before saying it is done.

| Layer | What | Where | Runs |
|---|---|---|---|
| Unit | Pure functions: validators, voting, geometry, config loading | `tests/unit/` | every commit, under 60 s, no models |
| Component | One stage on synthetic pages (comb removal, orientation, checkbox) | `tests/component/` | every commit, CPU only |
| Reader smoke | Each enabled reader loads and reads a synthetic crop | `tests/readers/` | marked `@pytest.mark.model`, skipped when the model is not installed |
| Integration | Full pipeline on synthetic packs → Excel matches the expected output | `tests/integration/` | before every PR |
| Evaluation | Full pipeline on the real test set (outside the repo) → scores | `python -m torus.eval run` | before merging any change that affects output |

Rules:

- **Synthetic fixtures only in git.** `tests/fixtures/synth/` contains generators that draw forms, comb boxes, handwriting-like strokes (from public handwriting fonts and datasets), stamps and rotations. Generated files are not committed. Generators are.
- **No test may depend on a specific real document.**
- A bug fix starts with a failing test that reproduces it (synthetic), then the fix.
- The evaluation report (field accuracy per column, silent-error count, automatic rate, review rate) is attached to the PR as a summary table. It contains **no document text**.
- **Regression gate:** a change that increases silent errors, or lowers accuracy on any column by more than the noise margin set in `config/pipeline.yaml`, is not merged.

Commands (after Phase 0 sets them up):

```bash
ruff format . && ruff check .
mypy src
pytest -m "not model"
pytest -m model            # only if the readers are installed
python -m torus.eval run --set dev --report reports/eval/latest.md
```

## 6. How an agent works on a task

1. **Pick** a task from `docs/IMPLEMENTATION_PLAN.md` (phase, task id). Work on one task at a time.
2. **Read** the relevant section of this file, the matching recipe in `SKILLS.md`, and the code you will touch.
3. **Plan** in a short note: what changes, which interfaces, which tests. If the task needs a decision that only a human can make (a new dependency, a schema change, a change to a protocol), stop and ask.
4. **Write tests first** where practical, then the code.
5. **Run** format, lint, types, unit, component and integration tests. If the change affects output, also run the evaluation.
6. **Report** in the PR or session: what changed, the test results, the evaluation table (before → after), known limits, and what a human should look at. Never claim a pass you did not run.
7. **Commit** small, focused commits with clear messages. Agents commit to a feature branch and **never push to `main`**. Pushing happens only when a human asks.

## 7. What humans do

- Check the evaluation table and the review samples. Decide whether the result is good enough.
- Approve new dependencies, protocol changes, template changes and model swaps.
- Look at the cases flagged `needs_review` and give feedback. Corrections flow into `learn/`.
- Own the real test set and answer keys (outside the repo).

## 8. Hardware

Developers have different machines. Hardware is **not** a design constraint of the pipeline. It only matters when you **enable a model**:

- Each reader in `config/readers.yaml` declares what it needs (`min_vram_gb`, `min_ram_gb`, `device`).
- `torus doctor` (Phase 0) detects the local machine and shows which readers can run here.
- Readers that cannot run are skipped automatically. They are never a crash.
- `docs/SETUP.md` lists the models, their sizes and where to put the weights.

Model weights never go in the repo. They go in the cache folder set by `TORUS_MODEL_DIR`.
